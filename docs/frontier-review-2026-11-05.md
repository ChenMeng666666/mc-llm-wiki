# 从记忆相关性走向可核查证据：2026-11-05 研究与实施记录

## 开发前：四个问题

目标是提高知识的可核查性，不扩大系统规模。本节在功能代码修改之前写下；后文补充源码核读与实测结果。原有未跟踪的 `docs/dsh-memory-investigation/` 属于已有工作，本次不修改。

### 1. 顶尖专家还会做什么

- 先检查已有实现，而不是按论文热度添加组件；把检索未命中、证据缺失、错误解读、来源不独立、维护遗漏分开。
- 主动找反例：一份论文的三次转述、部分共同来源的综合、循环血缘、缺失父来源，以及同一字节被赋予冲突的来源解释。
- 分开原始观察、论文作者的实验结论和本项目的工程推断；固定论文版本与代码 commit。新论文不自动比旧论文可靠。
- 固定条件做消融，保留负结果和停止条件。结构通过不等于语义正确；不同来源根也不自动代表独立实验。
- 在增加检索复杂度前，先让已有证据契约可以被工具检查。保留历史、只读查询和旧库兼容性。

### 2. 从哪些原始素材开始

| 原始材料 | 要核对的东西 | 不作为替代品 |
|---|---|---|
| arXiv 固定版本的方法、实验、消融与附录 | 支持集如何定义、预算怎么算、训练/测试如何隔离、结论边界 | 论文推荐榜和摘要拼接 |
| 作者发布的源码与实际调用路径 | 声明的溯源/校验是否实际执行、异常如何处理 | README 的功能列表 |
| 项目原始测试和评测入口 | 判据是否独立于模型答案、对照是否公平 | 产品宣传的跨榜最高分 |
| 本仓库 CLI、来源登记表、真实进程输出 | 数据是否真的沿声明的血缘流动、失败是否留下写入 | 已整理的研究总结 |
| 最小人工可算案例与程序生成的 DAG | 共同根、菱形依赖、深链和失效影响的准确集合 | 另一个模型表示同意 |

### 3. 具体方法与工具

先用 `rg` 和源码阅读定位数据流；用联网检索发现近期工作，再阅读一手原文。GitHub API 固定 commit，下载指定源码而不执行第三方代码。公开源码快照放在忽略的 `.evaluation/frontier-2026-11-05/`，记录 URL、hash 和阅读位置；网络失败单独记录。Python 标准库 `unittest`、`subprocess`、`tempfile` 对真实 CLI 做反例与回归测试；用独立的集合闭包算法作为图遍历的测试 oracle。比较修改前后，并做故障注入确认测试能抓住漏追溯。

### 4. 除了你我，什么能证明结果正确

证明范围分层：原文与固定源码证明设计借鉴可追溯；手算 fixture 和不同算法的 oracle 证明声明的血缘运算；原始文件 hash、整库前后字节对比证明快照核对和只读性；回归测试证明已有工具行为未被破坏。这些都不能证明原文事实为真、引用语义充分或实验独立。后者需要原始实验、领域复核，以及冻结的真实用户问题集；本次不得把作者自测称为独立模型评测或端到端质量提升。

## 开发前的本地证据与选型

原始基线：`python3 -m unittest discover -s tests -q`，26 项通过。

额外真实 CLI 探针发现两个现有测试未覆盖的问题：

1. 手工把来源 `derived_from` 改为指向自身，`lint` 仍退出 0。
2. 相同字节用不同 `kind/derived_from` 重新登记，返回成功去重，新的血缘意图被静默忽略。

这是来源契约的执行缺口；BM25 排名不涉及这两个问题。选定一个完整改进：**来源血缘审计**。沿已有 `derived_from` 追溯根，沿反方向找到需复核的断言；把循环、缺失父来源、冲突的重复登记明确暴露。不给根数量命名为置信度，也不自动撤销断言。复杂检索和自动事实裁决留待真实任务证据。

验收条件在实现前固定：

- 多条转述共同回到一个来源根；混合来源共享的根只出现一次。
- 原始来源变化时，可找到直接和多层派生引用的断言，并列出仍有的其他来源根；不把它们宣布为已失效或已获证实。
- 循环、无效血缘、冲突重复登记拒绝成功；错误不留下 raw/registry/事务副作用。
- 旧库未登记血缘的 derived 来源标明不完整，不能伪装成已找到原始根。
- 审计只读，不修改知识库；损坏快照不能得到成功的完整性背书。
- 人工案例、不同算法的图 oracle、深链和既有回归均通过。

## 开发结果与反对意见

实现只沿已有来源与断言契约加深：

- 新增 `evidence --claim` 与 `evidence --source`，分别报告声明根/缺口和上游变动的复核范围。各集合显式给出 total/truncated。
- `lint/apply/add-source` 拒绝来源图循环、缺父项、无效父列表；无父项的旧 derived 记录保留但明确不完整。
- 相同快照重复登记时，kind/scope/derived_from 的显式冲突报错且不产生写入；省略参数复用原登记，不影响 URL 别名去重。
- 查询流程增加必要子断言与原文证据对应；维护流程使用影响清单；评测分开原文可见性、语义正确性和完整提示成本。

为什么不只改提示词：自循环与静默丢血缘是可由确定性工具阻止的问题。为什么不自动否定受影响断言：多个父项可能是共同必需前提，也可能包含替代支持，当前 schema 没有表达这种逻辑；可达性不能裁决事实。为什么不直接加向量或图检索：本次复现的失败发生在检索之后的来源审计，改变排名不修复它们。

`other_roots` 仅是避开目标来源仍可到达的根。例如原文 A → 摘要 C，断言同时引用 A 和 C；C 出问题时 A 路径仍存在，但这并不能自动证明原断言。反之原文 A 出问题时，所有仅由 A 派生的转述均进入复核清单。没有登记的依赖、正文里的事实和 claim-to-claim 推理不在自动遍历范围。

工具始终返回 `semantic_support=not_checked` 与 `independence=not_checked`。没有声称更高回答准确率、具备自动充分性判断或完成长期维护评测。

测试环境：macOS / Python 3.14。全部运行脚本另以 Python 3.10 grammar 解析通过，未运行 Python 3.10 解释器。格式校验器直接运行时缺少 PyYAML，随后在 `uv --with pyyaml` 临时环境中通过；项目运行依赖仍为标准库。

修改前自循环 lint 成功、冲突重复登记成功；修改后相应反例被拒绝且保留原文件，形成明确的前后对照。测试与 oracle 由本次实现者编写，属于作者自测；算法不同不等于独立团队或盲测。原始本地测试输出为 `.evaluation/frontier-2026-11-05/tests.txt`，故障注入汇总为同目录 `mutation-results.json`；仓库内测试代码才是可携带的复现入口。

尚无真实用户 gold queries、端到端模型问答对照或长期维护测量，因此只主张修复来源结构契约，不主张语义正确率提升。若要继续，先冻结一小组真实失败问题、原始证据与反证，在相同完整提示预算下比较旧流程和新流程；出现可重复的语义召回缺口后再评估向量或多策略检索。
