# 从知识到技能

事实回答“是什么”；技能回答“在什么条件下如何做、怎样知道成功”。先把经验编译成带证据的模式，再蒸馏短而明确的操作技能。解释性事实留在 wiki，需要时链接；技能不能复制敏感项目数据或某次任务答案。

## 何时提炼

出现重复可迁移步骤、可验证的失败模式，或用户明确要求提炼时，生成候选。单次观察可以保存为候选假说，证据强度必须标明；不能把偶然成功变成无条件要求。用不同任务的正反例寻找触发条件、失效条件和环境依赖。针对某模型的补救标记模型/版本，避免伪装成普适最佳实践。

## 候选结构

在 `skill-candidates/<name>/` 写标准 SKILL.md、真正必要的 scripts/references，以及单独 evaluation.md：

- 适用任务、触发条件和排除条件；description 负责发现，不重复整个流程。
- 输入、预期结果、关键决策、验证方法、失败/中止条件。
- 非显然且有证据的程序知识；脚本只负责确定性重复工作。
- 支撑模式页、原 trace ID、已知反例、依赖/环境范围。
- 最小变更 diff；一次候选尽量只改一个技能的一类行为。

不自动修改当前启用的 llm-wiki、AGENTS 或其他 skill。用户明确要求更新现有技能时，可以在现有授权内完成候选与评测，再决定是否启用；证据不足则交付未启用的候选和缺口。

## 验证与晋升

先读 [evaluation.md](evaluation.md)。在查看结果之前固定开发集、独立验证集、指标和预算。相同 trace 既提供改法又作为唯一验证，不是泛化证据。检索和路由也要独立测试；全文注入好用不能证明 description 能召回。

保存基线版本，分别运行同条件的基线与候选。确定性任务用真实输出/外部 verifier；开放任务按可复核 rubric 检查来源正确性、覆盖、错误建议和成本，模型自评分只作辅助。至少覆盖正常路径、边界、反例与非触发请求。样例少时明确不确定性，不声称统计显著。

晋升条件由任务预先确定：硬性正确性/权限检查不能回退；目标质量改善，或质量不降且成本改善。与基线完全持平时通常保留原版本，避免无收益复杂度。任何未解释的重要退化阻止启用。不要在看到验证表现后调整门槛并继续称为独立验证。

记录候选 hash/diff、运行环境、基线和候选结果、预算、接受/拒绝及理由。拒绝时只丢弃候选激活，保留经验与评测记录以免重复试错；失败假说不能升级为事实。已启用版本留可回滚快照，出现实测退化时恢复上个已验证版本。研究式自动多轮进化是可选项目，不是普通 ingest 的默认成本。
